# 第一部分：项目现状

## 1.1 这是什么

「凡尘·需求台」（代号 `fanchen-desk`）是一个网页版原型。参考《不问凡尘》那种「与 NPC 对话、接取任务」的体验，但底层是**真实的 AI Agent**，不是写死的剧本。

现在的功能范围是 **L1**：玩家与 AI 角色聊天 → 话里出现需求 → 自动提取成任务 → 右侧任务清单。

| 层 | 选型 |
|---|---|

| 后端 | **零第三方依赖**，只用 `node:http` / `node:fs` / `node:path` + 全局 `fetch` |

**核心架构决策**：

1. **双通道需求提取**（ADR-003）
   - **工具通道**：给模型挂 `create_task` 函数，它自己决定何时登记（真正的 Agent 行为）
   - **抽取通道**：回复结束后先跑**纯函数规则引擎**打分，命中才调 LLM 做结构化抽取（省钱，不命中不调模型）
   - 两通道产出统一去重

2. **三级降级**
   - 模型不支持 tools → 去掉 tools 重试一次
   - 无凭据 → 降级为纯规则候选（标记 `origin: 'rule'`）
   - 模型返回非法 JSON → 容错解析 → 仍失败则回退规则

3. **协议收敛**（ADR-002）
   上游 OpenAI 兼容格式的差异（`delta.content` / `reasoning_content` / 分片 `tool_calls`）全部在服务端收敛成 **6 类 SSE 事件**，前端只认这套协议，换模型不用改 UI。

4. **状态集中**（ADR-005）
   `src/state/store.tsx` 是唯一可以触网、唯一读写 localStorage 的地方；`components/*` 保持纯展示。

# 第二部分：设计讨论全过程

> 这一部分保留推演脉络，因为它记录了「为什么最后是这个方案」，比结论本身更重要。

## 2.1 起点：最初的想法是「让 AI 写代码」

最初设想：在 Agent 对话中赋予 AI 编写代码的能力，游戏运行过程中根据需求在本地自动编写游戏功能。

**可行性结论**：技术可行，业界有大量先例（Claude Code / Cursor / Aider / OpenHands）。但瓶颈不在"写代码"，而在三件事：**验证闭环、安全边界、运行状态一致性**。

**关键建议**：不要直接改"正在运行的那份引擎代码"，把可被 AI 修改的部分收敛到一个受控 DSL / 配置层。

**方案分档**：

| 档位 | 形态 | 可行度 |
|---|---|---|
| L1 | 需求 → 任务清单（**当前原型就是这一档**） | 100% |
| L2 | 生成代码补丁 → 人工确认 → 应用 | 95% |
| L3 | 自动应用 + 自动验证 + 失败回滚 | 70% |
| L4 | 跑着游戏自己改自己、全自主 | ~30%，不建议产品化 |

## 2.2 方向修正：不是玩家的需求，是 NPC 的需求

**重要的理解修正**：现有原型记录的是**玩家的需求**，而新设计要的是 **NPC 的需求**——NPC 是任务发布者，玩家是接取方。这两件事在数据模型和裁决逻辑上是反的，不能直接套用。

**用户原话描述的场景**：

> 玩家与 NPC 交流，得知 NPC 想要获得什么、或想让玩家去做什么。
> 例如：交流得知该 NPC 有旧疾，需要一味药材才能医治 → 此时玩家选择是否接受这个寻草药的任务。
> 任务的奖励由 NPC 拟定：可能是自己背包内的道具，也可能是 NPC 自身的一些功能（比如《不问凡尘》里 NPC 存在的**结缘**、**切磋**等功能）。
> 提交任务时，在交流中（比如对话里出现「给与这个东西」的字眼）NPC 去检测玩家背包内的东西，自动扣除指定道具后完成任务。

**核心判断**：这个方向比"让 AI 写代码"安全一个数量级。因为 AI 不生成逻辑，只做**选择和填参**——输出空间是有限的、可枚举的、可校验的。

## 2.3 立住的第一条工程原则：AI 提意图，系统做裁决

**绝对不能让 LLM 直接改游戏状态，也绝对不能信任 LLM 的陈述。**

LLM 一定会说"好的，我收下这株三七了"——而玩家背包里根本没有三七。**这不是边缘 bug，是必然发生的事。**

| | 谁负责 |
|---|---|
| 识别"玩家表达了给予意图" | ✅ AI |
| 识别"给的是三七" | ✅ AI（歧义时给候选列表） |
| 判断玩家背包里有没有三七 | ❌ AI 无权，**代码裁决** |
| 判断任务是否处于可提交状态 | ❌ AI 无权，**代码裁决** |
| 扣除道具、发放奖励、改状态 | ❌ AI 无权，**代码执行** |
| 决定"这个 NPC 现在该不该有任务" | ❌ AI 无权，**门控驱动** |

**核心接口思路：给 AI 只读的真相，它就不需要猜。**

```js
// AI 可调用的工具 —— 全部是"提案"，没有一个是"执行"
inquire_inventory(who: 'player' | 'npc')    // 只读，消除幻觉的关键
propose_quest(want_ref, reward_ref, tone)    // 提案 → 系统校验 → 才生成任务卡
submit_quest_item(quest_id, item_id, count)  // 提案 → 系统校验背包 → 扣除 → 结算
decline_quest(quest_id, reason)
```

`inquire_inventory` 特别重要——它让 NPC 能"看见"玩家背包，从而不会说出"你上次给我的那株草"这种不存在的话。**幻觉的根治办法是给它事实，不是让它记住。**

## 2.4 第二次修正：玩家引导 = 涌现式隐藏任务

**用户补充**：

> 每个 NPC 在开始不是有提前设计好的提示词，有确定好的性格背景。
> 「玩家引导」的意思是：比如玩家说「我想多了解你一下」「有什么我能帮助你的」后，NPC 说出和自己背景的一些事去触发一些任务，**而不是由 NPC 对话强制获得这些任务**。
> 类似**隐藏任务**，但在游戏的任务系统中**不存在这个任务序列 ID**。
> 这个时候也会和 NPC 的性格有关联——比如一个 NPC 存在狡诈、爱骗人的性格，那可能会不给玩家奖励。

**这个补充推翻了一个前期建议**：曾建议过"槽位驱动、别让 LLM 凭空生成"，那是为了防玩家操纵。但用户要的恰恰是**涌现式内容**——任务不在任务表里，是聊出来的。槽位方案会把要的东西直接杀死。

**正确的调和点（三层分离）**：

| 层 | 谁定 | 自由度 |
|---|---|---|
| **触发时机**（能不能透露） | 代码 | 布尔判断，便宜、确定 |
| **叙事内容**（是什么故事、怎么说） | LLM | **完全自由 ← 涌现在这里** |
| **目标与奖励**（要什么、给什么） | 代码白名单 | 只能是枚举原语 |

> **代码控制「何时可以」，LLM 控制「是什么」。**

**"没有模板 ID" ≠ "没有记录"**：

```
Authored Quest    有模板ID、有剧情脚本、策划写的
Emergent Quest    运行时生成、无模板ID、来源是一次具体对话   ← 目标形态
```

一旦 NPC 说出口、玩家点头接受，它**必须立刻落库成一条真实任务实例**，否则会出现：刷新页面任务消失 / NPC 下次不认账 / 无法审计来源。

> **这部分原型里已经有雏形**：`Task.origin = 'llm' | 'rule'` 就是同一套思路（区分来源）。扩展成 emergent quest 只需加 `sourceDialogueId`、`loreId`、`provenance` 字段。

## 2.5 第三次修正：用户回答了 5 个待决问题

**用户原话**：

> **第一条（深聊触发的门槛）**：我有两种设想
> 1. 好感度不高的那种，需要通过对话，NPC 说出相关事宜后，玩家选择要不要去帮助
> 2. 好感度高的那种，会主动想让你帮助
> 好感度高低会影响任务的重要性。**一次性只会出现一个任务，当这个任务完成后，才会触发下一个任务**。而当 **NPC 背包里若没有可以用来当做奖励的内容则不会触发任务**了。
>
> **第二点（奖励体系）**：两者是一套体系，奖励只会是 NPC 背包内已有的道具或自身的一些功能（结缘啊等等）。当然奖励的多少 NPC 可与玩家商量来定，玩家可以不需要奖励（或者就是完成时加的好感度增多），不过必须是上面规定的内容。
>
> **第三个和第四个（狡诈 NPC）**：玩家必须知道自己是被骗了，后续可能玩家可以选择打 NPC 强制 NPC 拿出奖励，或者是利用一些其他的功能来获得这个奖励。
>
> **第五条（lore 一致性）**：我也没想到什么好的解决办法。我也不确定在与 NPC 聊天时，NPC 是怎么被玩家引导的，**这个度是怎么出来的**。

# 第三部分：已达成的设计结论

## 3.1 三层骨架（最重要）

> **叙事层自由涌现，门控层（阶段）由代码控，经济层（奖励）走守恒。**

三层各管一件事，互相不越界。原型里"玩家引导的度怎么出来"这个困惑，本质上就是**把"该不该说"从 LLM 手里拿走，交给代码**——拿走之后，"度"就变成一个可以调、可以测的参数了。

## 3.2 NPC 任务链机制

| 机制 | 说明 |
|---|---|
| **两条触发路径** | ① 好感度低：玩家需主动聊、慢慢磨 ② 好感度高：NPC 主动来托付 |
| **串行任务链** | **一次性只出现一个任务**，完成才触发下一个 |
| **好感度决定任务重要性** | 好感度越高，任务 tier 越高 |
| **奖励硬约束** | **NPC 背包里没有可发放的奖励 → 不触发任务** |
| **奖励守恒** | 奖励不是凭空印的，是从 NPC 转移到玩家（资源守恒） |

### ⭐ 其中「背包空了就不触发」是一个天然的完美闸门

这一条等于给经济系统装了一个**内生的、不用策划配表的天然闸门**。玩家刷不爆一个 NPC，因为刷完他就空了。这种东西通常要花很大力气做数值约束才能达到。

### ⚠️ 但三个机制叠在一起会撞出一个死角

```
好感度高 → 想做更重要的事 → 需要更贵重的奖励 → 背包里没有 → 触发不了
```

结果：**好感度越高，反而越没任务。**

**解法：道具有限，功能无限——正好互补**

| 好感度 | 任务重要性 | 奖励来源 | 会耗尽吗 |
|---|---|---|---|
| 低 | 小事（跑腿、带个话） | **NPC 背包道具** | ✅ 会，所以只给低价值 |
| 中 | 正事（寻药、了结旧怨） | 道具 + 少量结缘 | ✅ 会 |
| 高 | 大事（性命攸关、身世之谜） | **功能解锁（结缘/切磋/秘传）** | ❌ **不会，布尔锁是无限的** |

这样好感度高的 NPC 永远不会因为背包空了而"哑火"。而且功能解锁是布尔锁，**没有数值膨胀风险**——正好把最高价值的奖励放在最安全的形式上。

### 其他推论

- **背包枯竭应该是剧情节点，不是静默失效**：让 NPC 说出来——「我如今已身无长物，实在拿不出什么谢你……这一句谢字，你若不嫌，便收下吧。」然后给好感度/情报奖励收尾。**让枯竭变成一句台词，而不是一个静默的 false。**
- **婉拒的处理未定义**（见 §6 待决）
- **多个高好感 NPC 会同时来找你** → 需要全局节流（见 §6 待决）

## 3.3 奖励体系

**规则**：奖励只能来自 **① NPC 背包内已有的道具** 或 **② NPC 自身功能（结缘、切磋等）**，两者共用一套价值体系。数量可与玩家**商量**，玩家也可以**放弃奖励换取更多好感度**。

**奖励类型注册表**：

| 奖励类型 | 例子 | 数值风险 | 可撤销性 |
|---|---|---|---|
| `item` | NPC 背包里的丹药 | 中（会膨胀经济） | 可（回收） |
| `affinity` | 结缘度 +N | 低（有上限） | 可 |
| `ability` | 解锁"切磋"功能 | **无（布尔锁）** | 可（加锁） |
| `info` | 情报、线索 | 低 | 难 |

**三条硬约束**：

1. **奖励必须从白名单枚举里选**，不能凭空生成道具 ID
2. **数值由代码侧按稀有度/难度查表裁决**，LLM 只在允许区间内浮动
3. ⭐ **发布任务时要预留/锁定奖励**。否则同一个 NPC 背包里的那瓶药，会被两个任务同时承诺出去

**"商量"的技术约束**：别让 LLM 直接决定数值，让它**在档位里让步**：

```js
negotiate_reward(quest_id, offer_level)   // offer_level 是档位，不是具体数值
// 代码校验：offer_level ≤ maxLevel(npc.generosity, affinity, quest.tier)
//          且奖励物确实在 NPC 背包里 → 否则拒绝并回滚
```

玩家看到的自然语言谈判完全自由，但**每次让步都要过一遍代码校验**。

**⚠️「不要奖励换好感度」的平衡陷阱**：如果好感度收益太高，玩家会永远不要奖励，道具经济就失去意义。建议好感度加成是**固定小值**，或有上限/递减，让"要奖励"和"要好感"是两条不同的收益曲线。

## 3.4 性格系统与狡诈 NPC

**用户要求**：玩家必须知道自己被骗了；后续可以选择打 NPC 强制拿奖励，或用其他功能获得。

### 4.1 技术上它是两种奖励模式

| | 契约型 `bound` | 口头型 `unbound` |
|---|---|---|
| 发布时 | 奖励**预留锁定** | 只记录"口头承诺" |
| 完成时 | 必定发放 | 由性格/关系/随机**裁决** |
| 适用 | 大多数 NPC | 狡诈型 NPC |

硬要求：**提交道具那一步必须先落库**（道具真的被扣了），再裁决是否兑现。否则没法处理"吞了东西不给钱"这个状态。

### 4.2 红线：背叛必须「可察觉」

> **可被察觉的背叛 = 深度；不可察觉的背叛 = 挫败感。**

如果同一个 NPC 有时给、有时不给、毫无规律，玩家不会读作"他性格狡诈"，只会读作"这游戏有 bug"。

| 手段 | 说明 |
|---|---|
| **话术破绽** | 承诺时闪烁其词、答应得过于爽快、回避具体数额（prompt 就能做到，成本极低） |
| **名声系统** | NPC 有公开的 `honesty` 属性；别的 NPC 会评价他 |
| **前科记录** | 玩家被骗过一次后，之后所有对话框都带提示 |

### 4.3 ⭐ 关键工程点：赖账不能让奖励消失，要把它变成一笔「债」

如果 NPC 赖账后奖励物凭空没了，玩家"打他一顿"也拿不到东西——因为东西不存在了。

```
赖账 → 写入 debt ledger：{ npc, player, reward_ref, quest_id, reason }
     → 奖励物仍锁定在 NPC 身上（不可他用）
     → 玩家可通过多种手段兑现：威逼 / 战斗 / 揭发 / 交易 / 其他 NPC 施压
```

**`debt` 这一张表，把"被骗"从一个死胡同变成了一条新的内容线。**

⚠️ **隐藏依赖**：「打 NPC 强制拿奖励」依赖一个**还不存在的战斗系统**。在现有原型里需要先用替代出口（公开揭发、其他 NPC 施压、偷窃、任务胁迫）顶上。

### 4.4 性格必须落到代码，不能只写在 prompt 里

只在 system prompt 里写"你是个狡诈的人"是**不可靠的**。而奖励发不发是**游戏性行为**，必须确定。

```js
npc.traits = {
  honesty:    0.2,   // 守信度 → 是否允许 unbound 承诺
  generosity: 0.3,   // 慷慨度 → 奖励价值上限
  openness:   0.7,   // 坦诚度 → 背景透露门槛
}
```

- prompt 里注入这些数值的**自然语言描述** → LLM 表演一致
- 代码里用同样的数值做**裁决** → 结果确定
- **表演层和裁决层共用同一份数据**

⚠️ 细节：**prompt 里要禁止 NPC 说"我发誓""绝不食言"这类绝对承诺**，否则表演和裁决会打架——NPC 斩钉截铁地保证然后赖账，玩家会认定是 bug。让他搪塞、含糊、画大饼，但别让他发毒誓。

## 3.5 ⭐ 核心：引导的「度」到底怎么出来

### 5.1 先拆概念：所谓"引导"其实是两件事

```
引导 = 玩家用什么话术去问（输入侧，LLM 识别）
     × NPC 在什么条件下愿意说（门控侧，代码判定）
```

**"度"完全产生在第二部分。** 玩家话术再花哨，也只是"敲门的力度"；门开不开、开多大，是代码说了算。

**这就是防越狱的根本**：玩家没法靠话术把 NPC 骗出不该说的东西，因为门控不在 LLM 手里。

### 5.2 具体机制：分阶段揭示

不要让 NPC 对「有什么我能帮你的」给出**一次性答案**，而是让它的背景**分阶段释放**：

| 阶段 | NPC 会说什么 | 门控条件（代码判定） |
|---|---|---|
| **0 表面** | 天气、闲话、客套 | 无条件 |
| **1 有烦心事** | 「近日心里总有些放不下的事……」 | 与该 NPC 累计对话 ≥ 3 轮 |
| **2 说出轮廓** | 「我在找一味药，只是不知何处可得。」 | 好感度 ≥ 20 **且** 玩家主动问过 |
| **3 完整委托 + 奖励** | 说出完整需求、给出奖励承诺 | 好感度 ≥ 40 **且** 玩家明确表示愿意帮 |

**这套模型一次性回答了全部疑问**：

| 需求 | 在模型里的位置 |
|---|---|
| 好感度不高 → 要聊出来 | 从阶段 0 慢慢爬到阶段 2，**要磨** |
| 好感度高 → 主动找你 | 直接从阶段 2 或 3 开场 |
| **"度怎么出来"** | **度 = 门槛松紧 + 起始阶段**。高好感 = 门槛低 + 起点高 |

### 5.3 关键实现：代码算阶段，LLM 在阶段内表演

```js
const stage = computeRevealStage(npc, player, conversation);   // → 0 | 1 | 2 | 3
```

注入 prompt：

```
[当前可透露阶段：2]
你可以暗示自己需要一味药，但不要说出具体是哪一味，也不要提奖励。
```

**叙事完全自由，边界完全确定。**

### 5.4 顺带解决的两个问题

- **玩家话术越狱**：问到阶段上限就停住了，问不穿
- **一致性**：阶段推进是单向的、有记录的，NPC 不会"上一句说在找药，下一句说在找仇人"

## 3.6 目标原语白名单（易漏但很要命）

LLM 可以自由编故事，但**目标和奖励都不能自由发明**。

如果 LLM 提出"让我开心就行"，代码**没法判定完成**。所以 `objective` 也必须是**可验证原语**的组合：

```js
objective_primitives = [
  'has_item(player, item_id, count)',
  'deliver_item(player, npc, item_id, count)',
  'talk_count(npc, n)',
  'defeat(target)',
  'affinity_at_least(npc, value)',
]
```

> **奖励白名单 + 目标原语白名单 + 自由叙事** = 三层分离的具体落地。

## 3.7 lore 一致性方案

核心思路：**把"骨架"和"细节"分开对待。**

| 层 | 什么时候定 | 可变性 | 例子 |
|---|---|---|---|
| **authorred 设定** | 策划写死 | 永不可变 | 性别、身份、门派 |
| **骨架 lore** | **首次深聊时一次性生成并落库** | 生成后固化 | 有几个亲人、什么病、什么仇 |
| **细节 lore** | 每次对话现场生成 | 不固化，冲突无所谓 | 那天的天气、妹妹的乳名 |

**五条规则**：

1. **骨架预生成、细节现场编**。骨架（"有个失散的妹妹"）一次定死；细节（"她叫阿棠"）现场编，下次说成"阿棠儿"无伤大雅。**这一刀切下去，一致性问题的 80% 就没了。**
2. **生成即固化，不可覆盖**。写进 `npc.generated_lore[]` 后就是 canon。
3. **增量生成，不要重新生成**。给 LLM 的指令是"**接着说**"而不是"**说说你的身世**"——把已有事实列表给它，让它续写。重新生成必然漂移。
4. **冲突丢弃**。新生成内容若与已有 lore 冲突，直接丢弃重生成（用一次便宜的模型调用判定）。
5. **每轮注入摘要而非全文**（控制 token），放在 prompt **最前面**作为可缓存的稳定前缀。

**⚠️ 会立刻咬到你的坑**：如果 NPC 身世是现场生成又不落库——

> 玩家（第二次）："你上次说你有个失散的妹妹……"
> NPC："我没有妹妹啊。"

瞬间出戏。所以 `npc.generated_lore` 是必需的，不是优化。

# 第四部分：消耗与成本

## 4.1 实测磁盘占用（当前原型）

| 项 | 大小 |
|---|---|
| 手写源码（33 个文件） | **~0.3 MB** |
| `node_modules`（依赖） | **218.7 MB** |
| `.git`（完整历史） | 0.1 MB |
| `dist`（构建产物） | 0.3 MB |

**依赖体积是手写源码的 700 倍。** 这是所有"每加一个功能磁盘就涨"问题的根源。

## 4.2 「让 AI 写代码」方案的消耗（已否决，供对比）

| 任务规模 | 典型 token | 耗时 | 经济档 | 主流档 | 旗舰档 |
|---|---|---|---|---|---|
| 改文案/样式 | 1–3 万 | 20 秒–1 分 | <¥0.05 | ¥0.3–1 | ¥1–5 |
| 加一个小功能（含测试） | 10–40 万 | 3–15 分 | ¥0.2–1 | ¥2–10 | ¥10–50 |
| 加一个完整模块 | 50–200 万 | 15–60 分 | ¥1–5 | ¥10–50 | ¥50–250 |
| 从零搭一个这种项目 | 500 万–2000 万 | 数小时 | ¥5–20 | ¥50–300 | ¥300–1500 |

关键规律：
- **总 token ≈ 输出 token × 5~15 倍**（要反复读文件、看报错、重试）
- **输入（上下文）占总量 80–90%，输出只占 10–20%** → **prompt caching 是成本第一杠杆**（命中可省 ~90% 输入）
- 真正的成本杀手是**空转**：反复失败的任务能烧掉顺利情况下的 10–50 倍

其他消耗：构建峰值内存 +1–2 GB、无头浏览器 +300–400 MB（一次性）、每个并行 worktree +220 MB、建议预留 5–10 GB 磁盘。

## 4.3 NPC 任务系统的消耗（便宜一到两个数量级）

因为输出从"几千 token 的代码"变成了"几十 token 的结构化 JSON"。

| 项 | 量级 |
|---|---|
| 单轮对话 token | 2k–10k（含状态注入 + 对话历史） |
| 一次任务生成（工具调用） | +1k–3k |
| 一次深聊触发的背景生成 | 输出 +300–800 token（身世比任务描述长得多） |
| 经济档（DeepSeek 级）单轮成本 | < ¥0.01 |
| 一天 1000 轮对话 | ≈ ¥3–10 |

**新增的固定成本**：
- 每轮要注入状态摘要（进行中的任务、相关道具、NPC 阶段与 lore）→ 输入 token 上升
- NPC `generated_lore` 的存储与注入

**优化启示**：把 **NPC 人设 + 已生成 lore + 阶段状态**放在 prompt **最前面且保持格式稳定**，让它成为可缓存的固定前缀。几乎零成本、收益巨大。

# 第五部分：与现有原型的衔接

| 现有能力 | 能否复用 |
|---|---|
| SSE 事件协议 + 流式 tool_calls 拼装 | ✅ 直接用 |
| 候选卡 → 任务清单的交互 | ✅ 直接用，语义从"采纳需求"改成"接受委托" |
| 抽取通道（规则 + LLM） | ⚠️ 方向要反过来，改成 NPC 侧的提案 |
| 审计与溯源 | ✅ 直接用，而且更有价值（能查"这条任务为什么生成"） |
| 去重逻辑 | ✅ 直接复用（防止同一阶段反复出任务） |
| `create_task` 工具 | ❌ 要替换成 `propose_quest` / `submit_quest_item` |

**需要新增的核心部分**：
- **裁决层**（背包校验、奖励发放与预留锁、幂等、原子性、套利校验）
- **NPC 状态**：`traits`（性格参数）、`stage`（揭示阶段）、`generated_lore`、`inventory`、`debt_ledger`
- **Quest 表扩展**：区分 authored / emergent，加 `provenance`、`sourceDialogueId`

**架构不用推倒**，但裁决层是真正的工作量所在。

# 第七部分：下一步建议

**别先做对话，先做裁决层。**

先写死一个 NPC（就用"旧疾求药"这个例子）、一个道具表、一个奖励表，然后用**命令行方式**（不经 LLM）跑通完整链路：

```
发布任务 → 玩家接取 → 背包校验 → 提交 → 扣除 → 发奖励 → 状态流转
```

把**幂等、原子性、奖励预留锁、套利校验**全部测通。

> **这一层对了，接 LLM 只是把它变成一个"更灵活的输入方式"；这一层错了，接上 LLM 只会让 bug 变得更难复现。**

然后：第二步接对话 → 第三步接分阶段揭示 → 第四步开"玩家引导"。

**在动手前建议先钉死两样东西**：
1. `propose_quest` / `submit_quest_item` 的完整接口签名 + 校验规则表（含各种非法输入的拒绝策略）
2. **NPC 配置表**：把「性格参数 + 阶段门控条件 + 奖励档位」合成每个 NPC 一份的具体配置
