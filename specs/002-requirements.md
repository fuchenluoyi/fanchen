# 002 需求规格（含验收标准）

约定：`FR` = 功能需求，`NFR` = 非功能需求。
每条需求必须给出**可判定的验收标准（AC）**，验收时逐条勾选。

---

## 功能需求

### FR-001 对话区
系统 SHALL 提供与 AI 的多轮对话界面。

- AC-1.1 消息按时间顺序显示，区分 `user` / `assistant` 角色。
- AC-1.2 助手回复**逐字流式**渲染（首字延迟 < 3s 量级，取决于模型）。
- AC-1.3 `Enter` 发送、`Shift+Enter` 换行；空白输入不可发送。
- AC-1.4 生成中对话区自动滚动到底部；用户手动上滚时不强制拉回。
- AC-1.5 输入框在生成期间可继续输入，但发送被禁用（或走"中断并发送"）。

### FR-002 模型接入配置
系统 SHALL 允许用户在页面内配置 OpenAI 兼容服务。

- AC-2.1 可配置字段：`baseUrl`、`apiKey`、`model`、`temperature`、`systemPrompt`、`stream`、`enableTools`。
- AC-2.2 配置保存在 localStorage，刷新后仍在。
- AC-2.3 `apiKey` 以密码框呈现，默认不回显明文；提供"显示"开关。
- AC-2.4 若服务端设置了环境变量 `AI_BASE_URL` / `AI_API_KEY` / `AI_MODEL`，前端未填时自动使用并给出提示。
- AC-2.5 `baseUrl` 末尾斜杠自动归一化，不产生 `//chat/completions`。

### FR-003 连接自检
系统 SHALL 提供连通性自检。

- AC-3.1 顶部状态栏显示后端健康状态（`/api/health`）。
- AC-3.2 设置面板提供"拉取模型列表"（`/api/models`），成功时以下拉框供选择。
- AC-3.3 设置面板提供"测试对话"，发送一条极短消息并显示回显/错误。

### FR-004 工具通道（Agent 主动登记任务）
系统 SHALL 向模型暴露 `create_task` 工具，并在模型调用时把任务推给前端。

- AC-4.1 请求体携带 `tools: [create_task]`（当 `enableTools` 为真）。
- AC-4.2 服务端正确**拼装流式分片**的 `tool_calls`（按 `index` 聚合 `arguments` 片段）。
- AC-4.3 前端收到 `tool_call` 事件后，任务进入"候选卡"或直接入列（取决于 `autoAccept`）。
- AC-4.4 参数不合法（缺 `title`/`detail`）时被拒绝并记录审计信息，不产生脏任务。
- AC-4.5 若模型返回 400 且明确与 tools 相关，服务端自动**去掉 tools 重试一次**，并告知前端"该模型不支持工具调用"。

### FR-005 抽取通道（规则触发 + LLM 精抽）
系统 SHALL 在每轮助手回复结束后运行需求抽取。

- AC-5.1 先跑**规则引擎**；未命中则不调用 LLM（省成本）。
- AC-5.2 命中且具备凭据时，调用服务端 `/api/extract` 做结构化抽取，返回符合 `Task` 结构的结果。
- AC-5.3 LLM 返回非法 JSON 时，服务端做容错解析（去 ``` 围栏、截取首个合法 JSON 对象）。
- AC-5.4 LLM 抽取为空但规则命中时，回退使用规则候选。
- AC-5.5 `extractMode = off` 时完全跳过抽取通道。

### FR-006 无凭据降级
系统 SHALL 在没有可用凭据时仍能产出任务。

- AC-6.1 未配置 `apiKey` 且服务端无 `AI_API_KEY` 时，抽取通道仅使用规则引擎。
- AC-6.2 该类任务的 `origin` 标记为 `rule`，UI 上有可见标识。
- AC-6.3 不因缺少凭据抛出未捕获异常或阻塞对话。

### FR-007 任务卡确认入列
系统 SHALL 以"接任务"的方式让用户确认候选。

- AC-7.1 候选以卡片形式出现在任务面板顶部，显示标题、详情、优先级、来源（原话片段）、`origin`、置信度。
- AC-7.2 每张卡有"采纳"与"忽略"操作。
- AC-7.3 设置中开启 `autoAccept` 后，候选自动入列并给出轻提示。
- AC-7.4 采纳后卡片消失，任务出现在清单列表中。

### FR-008 任务清单管理
系统 SHALL 支持任务的完整生命周期管理。

- AC-8.1 字段：标题、详情、分类（feature/bug/content/question/other）、优先级（P0/P1/P2）、验收要点数组、状态、来源、创建/更新时间。
- AC-8.2 状态流转：`pending 待办 → active 进行中 → done 完成`，任意状态可 `dropped 废弃`。
- AC-8.3 提供状态筛选（全部/待办/进行中/完成/废弃）与计数。
- AC-8.4 可删除任务（二次确认）。
- AC-8.5 可按优先级排序展示。

### FR-009 去重与合并
系统 SHALL 避免同一需求反复入列。

- AC-9.1 候选入库前与既有任务做相似度比较，低于阈值直接丢弃。
- AC-9.2 相似度用字符三元组 Jaccard 计算（纯函数、可单测）。
- AC-9.3 同一轮回复内产生的多个候选之间也去重。
- AC-9.4 被丢弃的候选记录到审计日志（可查看原因）。

### FR-010 持久化
- AC-10.1 设置、消息、任务分别持久化到 localStorage（带版本号 key）。
- AC-10.2 版本不匹配或数据损坏时回退为默认值，不白屏。
- AC-10.3 提供"清空对话""清空任务""重置全部"三个操作，均需二次确认。

### FR-011 会话管理
- AC-11.1 "新建会话"清空消息但**保留**任务。
- AC-11.2 发送给模型的上下文只取最近 N 轮（默认 20 条），可配置。

### FR-012 错误呈现
- AC-12.1 网络失败、401/403、429、5xx 分别给出可读中文提示。
- AC-12.2 错误消息以特殊样式出现在对话流中，不打断后续对话。
- AC-12.3 服务端不把 apiKey 写入日志或错误响应。

### FR-013 停止生成
- AC-13.1 生成中显示"停止"按钮，点击后通过 `AbortController` 中断请求。
- AC-13.2 已生成的部分内容保留，并标记为"已中断"。

### FR-014 抽取审计
- AC-14.1 每条任务记录 `origin`（`llm` / `rule`）、`confidence`、`sourceMessageId`、`triggerReasons`。
- AC-14.2 UI 可查看某任务的来源消息（点击"查看原话"高亮对应消息）。
- AC-14.3 面板底部展示一次抽取的简要结论（是否触发、走了哪条通道、耗时）。

## 非功能需求

### NFR-001 零后端运行时依赖
- AC-1.1 服务端仅使用 Node 内置模块（`node:http`、`node:fs`、`node:path`、全局 `fetch`）。
- AC-1.2 `package.json` 的 `dependencies` 中不含服务端库（express 等）。

### NFR-002 构建产物体积
- AC-2.1 `dist` 中 JS 总计（gzip 前）≤ 600 KB，gzip 后 ≤ 250 KB。
- AC-2.2 构建无警告级别以上的报错。

### NFR-003 类型安全
- AC-3.1 `tsc --noEmit` 零错误，`strict: true`。
- AC-3.2 不使用 `any` 作为公共 API 类型（`unknown` + 收窄）。

### NFR-004 纯函数可测
- AC-4.1 规则引擎、相似度、去重、JSON 容错解析为**无副作用纯函数**。
- AC-4.2 这些模块可被 `node --test` 直接加载（不依赖 React/DOM）。

### NFR-005 可访问性基础
- AC-5.1 对话区 `aria-live="polite"`，任务计数有 `aria-label`。
- AC-5.2 所有交互元素可 Tab 到达，焦点样式可见。
- AC-5.3 颜色对比度 ≥ 4.5:1（正文）。

### NFR-006 安全
- AC-6.1 API Key 只存在于浏览器 localStorage / 服务端进程环境变量，服务端不落盘。
- AC-6.2 静态文件服务拒绝路径穿越（`..`、绝对路径、编码变体）。
- AC-6.3 代理接口只转发到配置的 `baseUrl`，且 `http/https` 之外协议一律拒绝。
- AC-6.4 请求体大小上限 1 MB。

### NFR-007 响应式
- AC-7.1 宽度 ≥ 1024px：左右两栏（对话 + 任务）。
- AC-7.2 宽度 < 900px：上下堆叠，任务面板可折叠。

### NFR-008 单命令启动
- AC-8.1 `pnpm dev` 同时启动前端 5173 与后端 8787。
- AC-8.2 `pnpm build` 产出 `dist`；`pnpm start` 由后端托管 `dist`，单端口可用。
- AC-8.3 **与包管理器解耦**：所有 npm scripts 内部只调用 `node`，不嵌套任何包管理器命令，因此 `npm run <x>` 与 `pnpm <x>` 完全等价（机器上没装 pnpm 时用 npm 即可）。
- AC-8.4 提供 `dev.cmd`：双击即可启动；脚本需以中文 Windows 的**本机编码（GBK/936）+ CRLF** 保存，否则 cmd 会把中文读成乱码并当成命令执行。

# 第二轮：NPC 委托系统

> **语义反转说明**：以上 FR-001~FR-014 描述的是「NPC 问玩家需要什么」；以下需求描述的是
> 「**NPC 自己需要什么，玩家去满足**」。两者是相反的对象，所以新增编号，不改写旧编号。
> 详细设计与校验规则表见 [008-npc-quest-domain.md](./008-npc-quest-domain.md)。

## 功能需求（第二轮）

### FR-015 道具与珍贵等级
系统 SHALL 提供道具白名单注册表，每件道具有珍贵等级、参考价值与用途标签。

- AC-15.1 珍贵等级五档：凡品 / 良品 / 上品 / 珍品 / 绝品，各带参考价值区间（1-5 / 6-20 / 21-80 / 81-300 / 301-1000）。
- AC-15.2 道具表**共 32 件、五档齐全（每档至少 5 件）**；每件道具的价值必须落在自己那一档的区间内
  （`auditItemTable()` 自检零问题）。
- AC-15.3 **既有道具 id 与定价不得改动或删除**（存档、既有委托与测试里有引用）。
- AC-15.4 每件道具有 `uses` **用途标签**，取自 12 个词的词表：
  疗伤 / 补血 / 调和 / 滋补 / 提神 / 吃食 / 器具 / 凭据 / 兵器 / 材料 / 信物 / 传信。
  `auditItemTable()` 的自检包含「uses 非空」与「标签必须在词表内」两条。
- AC-15.5 目标与奖励只能引用注册表内的道具 id，未登记一律拒绝（`unknown_item`）。
- AC-15.6 支持按名称、标签与用途检索，供模型在歧义时挑候选。

### FR-016 NPC 背包
系统 SHALL 为每个 NPC 配备背包，且玩家与 NPC 共用同一套背包结构。

- AC-16.1 背包分为「可用」与「已预留」两份；不变式：拥有总量 = 可用 + 已预留。
- AC-16.2 提供增加、扣减（可用）、预留、释放、核销五类**纯函数**操作，入参不被修改。
- AC-16.3 数量不足时操作失败并抛领域错误，背包保持原样。
- AC-16.4 NPC 背包拿不出奖励时，该 NPC 无法发布道具型委托（天然的奖励闸门）。

### FR-017 奖励系统
系统 SHALL 让奖励只来自 NPC 背包内的道具或 NPC 自身的功能。

> **原则（ADR-014）：有守恒的不设数值上限，没有守恒的才设。**
> 道具奖励是从 NPC 背包里真的挪走，有守恒；好感度发出去收不回来，没有守恒。

- AC-17.1 奖励类型白名单：`item` / `affinity` / `ability` / `info` / `none`（放弃奖励）。
- AC-17.2 档位三档：薄礼 / 中酬 / 重谢，由代码按「任务重要性（`tier`）× NPC 慷慨度（`generosity`）」算出
  （`maxOfferLevel`）；**模型不得自报档位** —— 工具参数与提案载荷里都不再有 `offer_level`。
- AC-17.3 **道具奖励不设价值上限**：再贵重也能当谢礼，只受两条硬约束 ——
  ① 必须出自该 NPC 的背包，拿不出来即拒（`reward_not_owned`）；
  ② 已被其他委托预留则不可用（`npc_reward_unavailable`）。
- AC-17.4 **好感度奖励保留档位上限**（薄礼 ≤ +3 / 中酬 ≤ +6 / 重谢 ≤ +10）：它没有守恒，所以要设上限。
- AC-17.5 功能解锁（结缘 / 切磋 / 秘传）只允许出现在「大事」上。
- AC-17.6 **发布委托时预留锁定奖励**，防止同一件道具被两个委托同时承诺出去。
- AC-17.7 婉拒 / 撤销 / 过期时释放预留；结算时核销预留并转移给玩家。

### FR-018 目标原语白名单
系统 SHALL 只接受可判定的目标原语，拒绝无法验证的目标。

- AC-18.1 原语集合：`deliver_item` / `has_item` / `talk_count` / `affinity_at_least` / `defeat`。
- AC-18.2 依赖尚不存在系统的原语（`defeat` 依赖战斗系统）拒绝登记（`unsupported_objective`）。
- AC-18.3 `deliver_item` 只能通过提交流程判定，不能靠读一眼背包就算完成。
- AC-18.4 `has_item` 判定不消耗道具。

### FR-019 涌现式 NPC 委托
系统 SHALL 允许委托在运行时现场生成，没有策划模板 ID。

- AC-19.1 委托记录 `provenance`（npcId / sourceDialogueId / draftedBy / createdAt），可追溯来源。
- AC-19.2 状态机：`offered → accepted → settled`，旁路 `declined` / `cancelled` / `expired`。
- AC-19.3 所求者（`requesterId`）恒为 NPC，接取方（`takerId`）恒为玩家。
- AC-19.4 同一 NPC 一次性只挂一个未完结委托（串行任务链）。
- AC-19.5 每次状态流转写入 `history`，每次裁决写入事件流水 `events`。

### FR-020 裁决层
系统 SHALL 由代码裁决委托的合法性；模型只提意图，不直接改世界。

- AC-20.1 每个操作要求 `requestId`；同一 requestId 重放只返回首次结果，世界不再变（幂等）。
- AC-20.2 同一 requestId 换参数复用被拒绝（`idempotency_key_reused`）。
- AC-20.3 任何校验失败都不改变世界（原子性），返回与入参逐字节一致的世界。
- AC-20.4 拒绝以 `{ ok:false, code, message }` 返回，code 覆盖校验规则表全集。
- AC-20.5 道具只在玩家与 NPC 之间转移，世界内道具总量守恒。
- AC-20.6 提供只读快照（`inspectNpc` / `inspectPlayer`）供模型与界面查询事实。

## 非功能需求（第二轮）

### NFR-009 领域层纯函数与零依赖
- AC-9.1 `src/lib/quest/` 不 import React / DOM / localStorage / fetch。
- AC-9.2 世界是可序列化纯数据，可整体克隆（原子性依赖这一点）。
- AC-9.3 全部逻辑可被 `node --test` 直接加载执行，允许使用 enum/namespace 之外的语法限制同 ADR-008。

### NFR-010 领域层可脱离 LLM 验证
- AC-10.1 提供 `pnpm run smoke:quest`（或 `npm run smoke:quest`）：不经 LLM 跑通
  「发布 → 接取 → 校验 → 交付 → 扣除 → 发奖 → 结算」。
- AC-10.2 冒烟脚本覆盖至少 5 条拒绝路径，并断言拒绝后世界不变（`JSON.stringify` 逐字节一致）。
- AC-10.3 冒烟失败必须以非零退出码结束。

# 第三轮：委托工具通道（T9）

### FR-021 委托工具通道（NPC 只提提案，不改世界）
系统 SHALL 让模型以**提案**的方式参与委托，绝不直接改世界。

- AC-21.1 请求体带 `questTools: true` 时，服务端在 `create_task` 之外暴露
  `propose_quest` / `submit_quest` / `decline_quest` / `note_impression` **四个**工具；不带该字段时行为与从前完全一致。
- AC-21.2 服务端只对工具参数做**形状**归一化（枚举 / 必填 / 类型）；失败发 `notice`
  （`code = quest_call_rejected`）并附可读原因，不产生脏数据。
- AC-21.3 归一化成功的提案经 SSE 事件 `quest_proposal` / `quest_submit` / `quest_decline`
  交给前端，由裁决层（FR-020）做规则裁决。
- AC-21.4 流式分片的 `tool_calls` 必须拼装完整后再归一化（沿用 FR-004 的拼装器）。
- AC-21.5 裁决拒绝的原因必须作为**事实**回注给模型，使 NPC 不得演出"已经收到东西"。

**实现状态**：AC-21.1 ~ AC-21.5 ✅（服务端见 008 §12，前端消费见 FR-022；交付动作与独立会话见 008 §12 第五轮）。

### NFR-011 服务端不复制领域规则
- AC-11.1 `server/lib/quest-tools.mjs` 不 import TypeScript 领域层
  （服务端要兼容 Node ≥ 20.11，而 .ts 类型剥离要求更高版本）。
- AC-11.2 服务端不持有世界状态、不做白名单与档位裁决；这些只有 `src/lib/quest/` 一处实现。

# 第四轮：前端接入与只读真相注入（T10）

### FR-022 NPC 委托接入界面
系统 SHALL 让 NPC 委托在界面里可见、可接取、可婉拒，并让 NPC 只能看见自己的视角。

- AC-22.1 设置新增「对话模式」：`npc`（默认）与 `desk`。**`desk` 模式的请求体、提示词、抽取通道、
  候选卡与去重行为与从前逐字节一致**。
- AC-22.2 `npc` 模式下请求体带 `questTools: true`（且 `enableTools` 为真），并注入 NPC 视角的只读真相。
- AC-22.3 只读真相**只含 NPC 自己的视角**：自己的背包（可用/已预留 + 等级与价值）、自己的委托、
  道具白名单（按珍贵等级分组）、玩家对自己的好感度。**绝不注入玩家背包**（ADR-013）。
- AC-22.4 `npc` 模式下不跑需求抽取通道（那是「玩家需求」的通道，与本模式语义相反）。
- AC-22.5 界面提供「委托」区：NPC 名与身份、委托（想要什么 / 目标 / 谢礼含等级 / 档位 / 状态）；
  `offered` 时给【接取】【婉拒】；`accepted` 时给**显式完成动作** ——
  交付型按钮带目标道具与数量（如「交付 三七×1」），非交付型为「请对方验看」，
  并显示玩家自己的持有量（不足时给警示样式但仍可点，判断交给裁决层）；点击同样走裁决层。
- AC-22.6 界面提供 NPC 背包**只读**区：可用道具（名称 / 等级 / 价值 / 数量）与已预留（被哪条委托锁着）。
- AC-22.7 三类委托事件一律走裁决层；**拒绝不得静默** —— 必须给出可见提示并记入审计。
- AC-22.8 世界持久化到独立 key（版本化），加载时容错归一化（最坏回到开局，不得白屏）；
  「重置全部」一并清空。
- AC-22.9 「出面 NPC」由设置决定，**模型无权指定**（提案载荷不含 `npcId`）。
- AC-22.10 上一轮裁决作为**事实**回注给模型，且**只回注一轮**（本轮没有新裁决即清空，避免旧拒绝被当成刚刚发生）。
- AC-22.11 `talk_count` 目标由前端记账：npc 模式下每完成一轮对话，为该 NPC 累计 +1。

### NFR-012 前端接入不新增依赖
- AC-12.1 本轮不修改 `package.json` 的 `dependencies` / `devDependencies`。
- AC-12.2 新增的前端逻辑尽量落在**纯函数**模块（提示词构建、事件→裁决接线、存档归一化），
  以便 `node --test` 直接覆盖；React 组件只做展示与按钮。

# 第五轮：交付动作 / 独立会话 / 道具与关系阶段 / 印象（T11）

### FR-023 关系阶段（五档，单向）
系统 SHALL 把好感度对外表达为**关系阶段**，并让阶段只影响态度、不影响许可。

- AC-23.1 五档：萍水 / 相识 / 知交 / 知己 / 莫逆；阈值 0-4 / 5-14 / 15-29 / 30-59 / 60+。
- AC-23.2 **单向不回落**：记录历史最高阶段（`player.stagePeak`），好感度掉回去也不降阶。
- AC-23.3 界面可见：对话区顶栏显示「关系 知交」+ 一格轻进度（还差多少到下一阶段）。
- AC-23.4 提示词注入**态度描述**：称呼、语气、愿不愿交底、会不会主动关心，随阶段递进。
- AC-23.5 **不做硬门闩**：阶段不得用于驳回任何提案；低阶段也能托付大事，只写进提示词引导
  （用户原话：事情可以说，就是态度的问题）。

### FR-024 印象与好感度
系统 SHALL 用 `note_impression` 工具承载「这话说到心坎里 / 冒犯了她」，并由代码管住频率与下限。

- AC-24.1 工具 `note_impression({ impression, reason? })`，`impression ∈ {pleased, neutral, offended}`；
  归一化失败照旧发 `notice`（`code = quest_call_rejected`）。
- AC-24.2 计分：`pleased` +2 / `neutral` 0 / `offended` −1。
- AC-24.3 **冷却**：同一 NPC 每 2 轮最多因印象涨一次（按对话轮数计，记在 `player.impressionGainAt`）；
  **`offended` 不受冷却限制** —— 说错话立刻有代价。
- AC-24.4 好感度下限为 0（clamp，不允许为负）。
- AC-24.5 幂等：同一 `requestId` 重放只生效一次；换参数复用被拒（`idempotency_key_reused`）。
- AC-24.6 每次成功的印象写入事件流水 `impression_noted`；它不属于任何委托（`questId = null`）。
- AC-24.7 客户端**每轮只处理第一条** `quest_impression`：重复调用不生效，但必须记入审计（不静默）。
- AC-24.8 新增拒绝码 `invalid_impression` / `impression_cooldown`，文案进 `ERROR_MESSAGE`。
- AC-24.9 提示词写明用法与"同一套恭维第二次不再新鲜"，并列出她的喜好与忌讳。

### FR-025 主观估值只做叙事
系统 SHALL 为 NPC 维护「她在意的 / 她多余的」，并**只**用于提示词与展示。

- AC-25.1 `NpcDef` / `NpcState` 携带 `wantsUses`（在意的用途标签）、`spares`（明确多余的道具 id）、
  `likes` / `dislikes`（自然语言短语）；三位 NPC 的背包**故意混着**两类，阿癞保持空背包（闸门样板）。
- AC-25.2 主观估值：命中 `wantsUses` → ×3（舍不得给）；命中 `spares` → ×0.5（拿出去换正好，**优先于** `wantsUses`）；
  其余 ×1。
- AC-25.3 提示词列出「我舍不得给的：三七、当归…」「我留着没用的：百年灵芝…」，
  并写明"系统**不会**因为"我舍不得"就驳回你的提议"。
- AC-25.4 委托面板的背包区展示同类标记（舍不得给 / 多余）与「她在意的用途」。
- AC-25.5 **绝不作为驳回依据**：裁决层不得引用主观估值（既有六个操作与印象操作都不读它）。

## 非功能需求（第五轮）

### NFR-013 叙事与裁决的边界
系统 SHALL 让叙事与裁决各守其位：能用嘴表达的，不用拒绝码表达。

- AC-13.1 主观估值（FR-025）、关系阶段（FR-023）、喜好倾向一律**不得成为硬门闩**。
- AC-13.2 唯一能做硬判定的仍是**守恒类约束**：库存是否够、是否已被预留、幂等键、目标原语白名单
  （含依赖缺失的 `unsupported_objective`）。
- AC-13.3 提示词与界面可以引用叙事状态；裁决层不得调用只做叙事的推导函数。
- AC-13.4 单测覆盖这条边界：断言主观估值不进入裁决路径、阶段不出现在任何驳回句式里。

# 第六轮：玩家背包 / 赠送 / 交付事实（T12）

### FR-026 玩家背包可见
系统 SHALL 让玩家看得见自己背包里的全部道具。

- AC-26.1 新世界（`createWorld` 默认）下玩家持有**道具表全部 32 件**，每件至少 1 件；
  显式列出的条目保持原量、**不重复加**（三七 1 / 甘草 2 / 干粮 2），同一件道具在背包里只出现一次。
- AC-26.2 只影响**新世界（新存档）**；旧存档保持原样，不做隐式补领迁移。
- AC-26.3 `npc` 模式下界面提供「我的行囊」：全量道具按珍贵等级由低到高列出，
  显示每件持有量，零持有置灰；位置在「需求清单」空态提示的下方。
- AC-26.4 玩家背包只用于展示与裁决，**绝不注入提示词**（ADR-013）；`desk` 模式不渲染该面板。
- AC-26.5 `auditWorld` 恒为空；玩家侧 `holds` 必须为空。

### FR-027 赠送（白送道具给 NPC）
系统 SHALL 支持玩家把道具白送给 NPC，与委托无关。

- AC-27.1 裁决层新增 `giftItem(world, { requestId, npcId, itemId, count, now? })`：
  `requestId` 幂等、改动只在草案世界上、失败丢弃草案（返回入参世界）。
- AC-27.2 **不产生委托、不改委托状态**；`Applied.quest` 恒为 `null`。
- AC-27.3 守恒：道具从玩家背包转移到 NPC 背包，`worldTotalOf(item)` 前后相等。
- AC-27.4 拒绝码只来自守恒类：`invalid_gift_count`（件数非正整数）、`unknown_item`、`unknown_npc`、
  `player_item_insufficient`、`idempotency_key_reused`；文案进 `ERROR_MESSAGE`。
- AC-27.5 **NPC 不得以「不喜欢 / 用不上」为由拒收**（NFR-013 / ADR-016）：只要玩家拿得出来，赠送必然成立。
- AC-27.6 成功写事件 `item_gifted`（`questId = null`）、动作文案「赠送」；界面「送给他」按钮走
  `store.giftQuest` → 裁决层，拒绝绝不静默（玩家侧文案）。

### FR-028 交付事实的权威来源
系统 SHALL 让 NPC 对「东西到没到」的认知来自世界状态，而不是上一轮消息。

- AC-28.1 提示词里每条委托必须**现算**「已经收到的货」，来源是 `Quest.delivered`
  （「道具真的被扣掉那一刻」的落库记录），不依赖 `lastRuling`。
- AC-28.2 已 `settled` 的委托必须明示「已经了结」：禁止再让对方交付一次，禁止说「东西呢 / 我还没见着」。
- AC-28.3 交付事实不随轮次过期：本轮没有新裁决时，**最近一次成功**的裁决事实继续回注；
  拒绝仍只活一轮（它是即时纠正，过期留着会被当成「刚刚又被拒了」）。
- AC-28.4 提示词仍然不含玩家背包（ADR-013）：交付事实只说「收到了什么」，不说「对方还剩什么」。

# 第七轮：人格分槽 / 行囊补齐 / 重置 / 留言 / 谢礼清单（T13）

### FR-029 人格补充按 NPC 分槽
系统 SHALL 让每位 NPC 有各自的人格补充，不再共用一份。

- AC-29.1 `Settings` 新增 `npcPersonas: Record<string, string>`（key 只认 `NPC_IDS` 那三位）；
  值 trim 后为空的丢弃，未知 key 直接忽略。
- AC-29.2 旧版本写在全局 `systemPrompt` 里的那段补充**不迁移**（否则会串到三个人身上），由玩家按 NPC 重填。
- AC-29.3 设置界面可切人编辑：只显示、只修改当前那一位；「清空」只清当前那一位。
- AC-29.4 `desk` 模式的 `systemPrompt` 路径**一字不改**；npc 模式取 `npcPersonaFor(settings, npcId)`。

### FR-030 行囊补齐（每件 64）
系统 SHALL 提供一键补给：不动设置/对话，把玩家每种道具补到目标数量。

- AC-30.1 裁决层新增 `restockPlayerInventory(world, { requestId, target? })`，默认 `target = 64`；
  **只补缺口**：已有数量 ≥ 64 的不动，因此重复点击不会越补越多。
- AC-30.2 幂等（同一 `requestId` 只补一次）；没有缺口时原样返回同一个世界。
- AC-30.3 它**故意不守恒**（世界补给，不是玩家↔NPC 转移），单独成一个操作，不混进交付/赠送路径；
  成功写事件 `items_restocked`，动作文案「补齐行囊」。
- AC-30.4 界面：「我的行囊」面板头部按钮「补齐行囊（每件 64）」。

### FR-031 重置对话与进度（保留设置）
系统 SHALL 提供只清「对话与进度」的重置，**不动设置与 API Key**。

- AC-31.1 清除对话、任务、委托世界三份本地数据；`settings`（含 API Key、模型、按 NPC 人格）保留。
- AC-31.2 与「清空全部本地数据」并列，文案必须写清两者差别。

### FR-032 结算后 NPC 留言
系统 SHALL 在委托了结后让 NPC 留一句话。

- AC-32.1 `questLetter(quest, npc)` 是**确定性纯函数**：同一条委托永远同一句，不额外调模型。
- AC-32.2 只有 `settled` 的委托才有留言；文案包含 NPC 名字、收到的货、按轻重的一句话、按奖励类型的一句话。
- AC-32.3 结算发生时（界面按钮或对话里提交）把留言追加到该 NPC 的对话线索；幂等重放（`applied` 为空）不重复追加。
- AC-32.4 委托卡在 `settled` 状态显示这条留言。

### FR-033 谢礼只能从自己背包里挑
系统 SHALL 让模型的谢礼承诺必须落在它真正拿得出的道具上。

- AC-33.1 提示词把「可用的道具清单」改名为「道具 id 拼写表」，并明示**它不是**能拿出的东西的清单。
- AC-33.2 新增「我能拿出的谢礼」：从 `listAvailable(npc.inventory)` 现算，逐件带数量；
  空背包直接写「一件也拿不出来」。
- AC-33.3 奖励被拒（`reward_not_owned` / `npc_reward_unavailable`）时，裁决事实必须给出可执行指引：
  换一件拿得出的、**重新调用 `propose_quest`**，不得重复原承诺。
- AC-33.4 单测：苏晚照的谢礼清单里不出现竹哨（竹哨只归陆行舟）；白名单仍列全表但已改名。
