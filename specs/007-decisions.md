# 007 决策记录（ADR）

格式：`ADR-xxx 决策标题 / 状态 / 背景 / 决定 / 理由 / 代价`

---

## ADR-001 后端零运行时依赖
**状态**：已采纳（T1）
**背景**：需要一个代理层来隐藏 API Key、规避 CORS、统一处理流式工具调用。
**决定**：服务端仅用 `node:http` / `node:fs` / `node:path` 与全局 `fetch`，不引入 express/fastify。
**理由**：代理逻辑只有 4 个接口；少一层依赖即少一份升级与供应链风险；安装体积更小。
**代价**：自己写 body 解析、路由、静态托管与 SSE 编码（约 200 行）。若将来接口膨胀到 10+ 个，再评估迁移到框架。

## ADR-002 自定义 SSE 事件协议，而非透传上游
**状态**：已采纳（T2）
**背景**：上游 OpenAI 兼容服务的流格式存在差异（`delta.content`、`delta.reasoning_content`、分片的 `tool_calls`），若前端直接解析会让 UI 与厂商强耦合。
**决定**：服务端收敛为 6 类事件：`delta / reasoning / tool_call / notice / usage / done / error`，其中 `tool_call` 只发**已拼装完整**的参数对象。
**理由**：前端逻辑简单稳定；换模型不影响 UI；分片拼装这种易错逻辑集中在一处并有单测覆盖。
**代价**：新增一层协议需维护；上游出现新特性时要手动映射。

## ADR-003 需求提取采用"双通道"
**状态**：已采纳（T4）
**背景**：只靠模型 function calling，遇到不支持工具的模型就完全失效；只靠事后抽取，又丢掉了 Agent"主动接任务"的体验。
**决定**：通道 A（工具）——模型主动调用 `create_task`，即时性好；通道 B（抽取）——回复结束后由规则触发，命中才调 LLM 做结构化抽取。两通道产出的候选统一去重。
**理由**：体验与鲁棒性兼得；规则先筛，省掉大量无谓的 LLM 调用。
**代价**：同一需求可能被两个通道各报一次，必须做去重（FR-009）。

## ADR-004 无凭据时降级为纯规则候选
**状态**：已采纳（T4）
**背景**：用户可能还没填 Key，或服务端未配置环境变量。
**决定**：规则引擎独立成纯函数并产出候选（标题取句子截断），任务照常进清单，`origin='rule'` 明示。
**理由**：空 Key 也能演示完整链路；规则结果质量差但可接受，且用户可见来源。
**代价**：规则候选标题较粗糙，需要用户在采纳时手动润色（当前版本不做内联编辑，列为后续增强）。

## ADR-005 状态用 Context + useReducer，不引状态库
**状态**：已采纳（T5）
**背景**：状态树很小（消息、任务、候选、设置、审计）。
**决定**：单一 `useReducer` + Context，副作用集中在 `send()` 与持久化 `useEffect`。
**理由**：零新依赖；状态迁移可枚举、易调试；符合架构约束"组件不直接触网"。
**代价**：状态变大后需要拆 context 或引入选择器优化重渲染。当前规模无此问题。

## ADR-006 持久化用 localStorage（版本化 key）
**状态**：已采纳（T5）
**背景**：原型阶段没有账号体系，但用户不希望刷新丢任务。
**决定**：`fanchen.settings.v1` / `fanchen.messages.v1` / `fanchen.tasks.v1`，读取时校验版本与结构，损坏即回退默认值。
**理由**：零成本、离线可用、隐私友好（数据不出本机）。
**代价**：换浏览器/设备不同步；容量约 5 MB，长对话需截断（`historyLimit`）。

## ADR-007 UI 采用矩形框简洁风格
**状态**：已采纳（T3）
**背景**：原始设想是水墨卷轴风，但用户明确"先不需特别格式，用矩形框实现即可"。
**决定**：纯 CSS 矩形卡片 + 1px 边框 + 中性配色，不引入 UI 组件库、不使用图片素材。
**理由**：聚焦功能验证；后续换皮只需改 `styles.css` 与主题变量。
**代价**：视觉表现力弱于游戏化方案（已列入后续增强）。

## ADR-008 测试用 `node --test` + 原生 TS 剥离
**状态**：已采纳（T6）
**背景**：领域层是纯函数，值得单测；但不想为测试再装 vitest/jest。
**决定**：Node 24 原生类型剥离直接运行 `.ts` 测试文件；相对导入统一带 `.ts` 扩展名（`allowImportingTsExtensions` 已开启，Vite 同样支持）。
**理由**：零测试依赖，`pnpm test` 秒级反馈。
**代价**：不能使用 enum / namespace / 参数属性等需编译的 TS 语法（领域层本就不需要）。

## ADR-009 默认指向 DeepSeek 的 OpenAI 兼容端点
**状态**：已采纳
**背景**：用户希望"接入当前的 AI"。
**决定**：默认 `baseUrl=https://api.deepseek.com/v1`、`model=deepseek-chat`，用户可改成任意 OpenAI 兼容端点；服务端支持 `AI_BASE_URL/AI_API_KEY/AI_MODEL` 环境变量兜底。
**理由**：开箱即用，同时不锁死厂商。
**代价**：无（默认值仅为占位，用户可覆盖）。

## ADR-010 NPC 委托领域层独立于 UI 与服务端
**状态**：已采纳（T8）
**背景**：委托要从「玩家的需求」反转成「NPC 的需求」，还牵出背包、道具等级、奖励、裁决一整套规则。直接塞进现有 store 或后端，会让"规则对不对"和"界面好不好"两件事互相纠缠，出错时无法定位。
**决定**：新开 `src/lib/quest/` 纯领域层：不触网、不碰 DOM、不读写 localStorage；世界是可序列化纯数据；先用单测与命令行冒烟把规则钉死，之后再决定接前端还是接服务端。
**理由**：交接文档 §7 的判断 —— 这一层对了，接 LLM 只是换个输入方式；这一层错了，接上 LLM 只会让 bug 更难复现。
**代价**：这套领域层暂时没有界面，只能靠命令行与单测看效果；接入 UI 时还要再写一层适配。

## ADR-011 奖励用「预留锁」，而不是「发布时即扣」
**状态**：已采纳（T8）
**背景**：同一个 NPC 背包里的同一瓶药，可能被两个委托同时承诺出去；但委托还没完成就把奖励扣走，玩家婉拒后又要还回来。
**决定**：背包分「可用」与「已预留」两份。发布委托时把奖励从可用挪进已预留（锁定）；婉拒 / 撤销 / 过期时释放回可用；结算时核销并转移给玩家。不变式：拥有总量 = 可用 + 已预留。
**理由**：一次挪位同时解决"重复承诺"与"婉拒归还"两个问题，而且天然守恒。
**代价**：背包查询要区分"可用"与"拥有"两个口径；每件被承诺的奖励都多出一条预留记录。

## ADR-012 裁决层用「草案世界 + 整体提交」保证原子性
**状态**：已采纳（T8）
**背景**：一次提交要同时做四件事（扣道具、转背包、发奖励、改状态），中间任何一步失败都不能留下半成品。
**决定**：每次操作先深拷贝一份草案世界，全部改动都发生在草案上；任何校验失败就丢掉草案、返回与入参**同一引用**的原世界；成功则整体提交。配合 `requestId` 幂等记录，重放不会二次生效。
**理由**：不写回滚代码，就不存在"回滚写漏一笔"的可能；"拒绝 = 世界逐字节不变"可以直接用 `JSON.stringify` 断言。
**代价**：每次操作多一次深拷贝（本数据量下可忽略）；世界必须保持纯数据，不能持有函数或定时器。

## ADR-013 只读真相只给 NPC 自己的视角，不给玩家背包
**状态**：已采纳（T9）
**背景**：原本设想给模型一个 `inquire_inventory(who)` 工具，让它自己查背包。但"东西交没交到"本来就由代码核对，让 NPC 去"看"玩家背包既不必要，又把幻觉的口子留在了最关键的地方 —— LLM 一定会说"好的，我收下这株三七了"，而玩家背包里根本没有三七。
**决定**：注入给模型的只读真相**只包含 NPC 自己的视角**：自己的背包（可用 / 已预留）、自己的委托（含状态）、道具白名单、玩家对它的好感度。**不注入玩家背包**。玩家是否真的交付，由裁决层在提交时核对；NPC 对"交付已发生"的认知来自**委托状态变化**，而不是背包读数。裁决结论（尤其是拒绝原因）作为事实回注，供 NPC 下一轮表演。
**理由**：把交付判定从"模型的陈述"彻底移到"代码的事实"，这一处幻觉是被**根除**而不是被提示词压制；同时省掉一次工具往返与一整套多轮工具循环（当前管道是一问一答，支持回环的成本明显更高）。
**代价**：NPC 无法主动引用玩家背包里的具体物品（"你身上那味药"说不出口）。目标该由委托定义，而不是由窥探玩家口袋决定；若将来确实需要，再引入受控的只读查询工具。

## ADR-014 有守恒的不设数值上限
**状态**：已采纳（T11）
**背景**：奖励原本按「档位 × 价值上限」裁决（薄礼 ≤20 / 中酬 ≤80 / 重谢 ≤300），于是出现"小事给不起百年灵芝"这类拒绝；更糟的是档位可以**由模型自报**，她一句"我出重谢"就能把上限顶开，成了翻车的源头。
**决定**：**道具奖励取消价值上限**，只保留两条硬约束 —— 必须出自 NPC 自己的背包（`reward_not_owned`）、已被其他委托预留则不可用（`npc_reward_unavailable`）；**好感度奖励保留档位上限**（`OFFER_LEVEL_AFFINITY_CAP`）；功能解锁仍限「大事」。档位不再由模型自报，一律由代码按「事情轻重 × 慷慨度」算出。
**理由**：道具奖励的膨胀风险本来就由**背包有限**挡住了 —— 给出去的每一件都是从她背包里真的挪走，有守恒，就不需要再叠一层数值上限；好感度发出去收不回来，**没有守恒**，才需要设上限。一条原则比两张表好记，也不会再出现"她自报档位"这个口子。
**代价**：模型可能一时大方，把家底一次性掏空。接受：掏空了就再发不出任务（背包枯竭是天然闸门，阿癞就是那个样板）。

## ADR-015 关系阶段取代数值门闩
**状态**：已采纳（T11）
**背景**：好感度原本只是一个数字（界面显示"好感度 18"）。若用数字做硬门控（"好感度 <30 不许托付大事"），玩家会遇到"问不穿"的挫败：同一个人反复问、永远被拒，却看不出差在哪。
**决定**：对外只暴露**阶段名**（萍水 → 相识 → 知交 → 知己 → 莫逆，阈值 0/5/15/30/60），阶段影响的是**态度**（称呼、语气、愿不愿交底、会不会主动关心），而不是"能不能说 / 能不能提"。阶段**单向不回落**（记历史峰值，好感掉了不降阶）。低阶段可以托付大事 —— 代码不拦，只写进提示词引导。
**理由**：态度描述比数字更能让模型演对；"事情可以说，就是态度的问题"（用户原话）符合"AI 提意图、系统做裁决"的分工 —— 语气是模型的活，门闩才是代码的活。
**代价**：模型偶尔会在低阶段显得过于亲近；靠提示词与印象负分（FR-024）收敛，不靠拒绝。

## ADR-016 主观估值只进叙事
**状态**：已采纳（T11）
**背景**：NPC 对同一件东西的主观估值并不相同 —— 苏晚照觉得三七值钱（舍不得给），灵芝在她眼里只是存货（拿出去换正好）。这层关系很容易被顺手写成一条裁决规则（"她舍不得的东西不许当奖励"）。
**决定**：`wantsUses`（在意的用途）/ `spares`（多余的）/ `likes` / `dislikes` 只用于推出**主观估值**（×3 / ×1 / ×0.5），并且**只进提示词与展示**（"我舍不得给的：三七、当归…"），**绝不作为驳回依据**。
**理由**：一旦当硬规则，就会出现"她自己想给的东西，系统不许她给"这种反叙事，玩家也读不懂为什么被拒；叙事层的不情愿应该由 NPC 用嘴表达，而不是由代码用拒绝码表达。
**代价**：模型可能一时不讲价，把舍不得的东西也痛快给出去。可接受 —— 这是叙事质量问题，不是正确性问题。
